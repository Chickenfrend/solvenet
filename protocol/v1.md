# SolveNet local worker protocol v1

HTTP JSON, UTF-8. This prototype listens on loopback and has no authentication.
Run one coordinator process per database. Do not expose its API publicly.
Requests are limited to 256 KiB, except result submissions, which allow 2 MiB
for the candidate and raw response including JSON escaping. Errors are
`{ "error": "description" }`, encoded as UTF-8 JSON with
`Content-Type: application/json`. This envelope also applies to HTTP parsing and
method errors generated by the coordinator. A POST request without
`Content-Length` returns 411; an invalid length or malformed UTF-8/JSON body
returns 400; an oversized body returns 413. Unsupported methods return 405 with
`Allow: GET, HEAD, POST` rather than the standard library's HTML 501 response.
The coordinator owns a single pinned Lean environment; workers do not select it.

### Wire limits and ownership

The following are v1 protocol bounds. String sizes count UTF-8 bytes after JSON
decoding; HTTP request sizes count the encoded body bytes, including JSON escapes.
The named definitions are `coordinator/src/solvenet/protocol_limits.py` and
`worker/internal/daemon/limits.go`. Both implementations enforce the fields they
receive; a sender must keep its own outbound fields within these bounds.

| Wire value | Maximum |
| --- | ---: |
| Identifier, model, import module, generation model/finish reason | 256 bytes each |
| Statement | 64 KiB |
| Imports and claim model list | 32 entries each |
| Messages | 32 entries |
| Message content | 256 KiB per entry |
| Candidate (`output.text`), `generation.raw_response` | 128 KiB each |
| Failure/rejection error | 4096 bytes |
| `max_output_tokens` | 32768 |
| Generation timeout, heartbeat interval | 86400 seconds |
| Non-proof task messages | 8 entries, 8 KiB content each |
| Non-proof task result (`output.text`) | 8 KiB |
| Non-result request body, result request body | 256 KiB, 2 MiB respectively |

These are maxima, not defaults. Required text fields must also be nonempty;
messages may be an empty array. Coordinator-issued path IDs have the narrower
32-lowercase-hex syntax; the 256-byte identifier bound on assignment fields
allows opaque credentials. Local limits such as Ollama's 1 MiB HTTP response
cap, its configured context size, Docker/Lean resource limits, repair count,
attempt count, and assignment retries are implementation or experiment policy,
not interchangeable with the v1 wire bounds. See
[`docs/ticket-17-protocol-limits.md`](../docs/ticket-17-protocol-limits.md).

Routing uses the URL path, not the complete request target, so query parameters
do not alter endpoint matching. Path segments are percent-decoded as UTF-8 and
must use valid percent escapes. Run and assignment identifiers in endpoint paths
must be coordinator-issued 32-character lowercase hexadecimal identifiers;
clients should continue to treat them as opaque values. Empty, extra, or invalid
segments do not match an endpoint. `HEAD` uses the corresponding `GET` status
and headers, including the representation's `Content-Length`, but sends no body.

## Submit and inspect a run

A problem is the stored Lean statement and imports. A run is one submission of
that problem with a search policy and one or more requested models. The simple v1 submission
field `attempts` counts initial search chains: each starts with one initial job
and can add repair jobs after rejected candidate proofs. It does **not** count
completed candidate attempts in the `attempts[]` inspection collection. Initial
chains need not run on different workers or represent distinct logical agents;
the same worker may claim several jobs. See
[the terminology glossary](../docs/ticket-18-terminology.md).

`POST /v1/runs`:

```json
{"statement":"(n : Nat) : n + 0 = n","imports":["Init"],"attempts":3,"model":"scripted","max_output_tokens":2048,"max_repairs":0,"max_assignments":3,"generation_timeout_seconds":120}
```

Returns 201 with `problem_id` and `run_id`. Defaults are shown except for the
required statement. `attempts` is 1–100; `max_output_tokens` is 1–32768.
Alternatively, submit ordered initial-job groups:

```json
{"statement":"(n : Nat) : n + 0 = n","initial_jobs":[{"model":"ollama/model-a","count":2,"max_output_tokens":256},{"model":"ollama/model-b","count":1}]}
```

Each group requires a nonempty `model` (at most 256 UTF-8 bytes) and integer
`count` (1–100); its `max_output_tokens` defaults to 2048 and must be 1–32768.
The array must have 1–100 groups, with a **total** count of 1–100 initial jobs.
Unknown group fields are rejected. When `initial_jobs` is present, `attempts`,
`model`, and top-level `max_output_tokens` must all be absent, even if set to
their old defaults. The existing single-model form and its defaults are unchanged.
`imports`, `max_repairs`, `max_assignments`, and `generation_timeout_seconds`
remain shared run settings. Jobs are inserted group-by-group in array order.

`max_repairs` is an integer 0–2 (default 0), and `max_assignments` is an integer
1–100 (default 3). Let `A` be `attempts` in the simple form or the sum of group
counts in the grouped form. At most `A * (1 + max_repairs)` jobs can be created;
each job has at most `max_assignments` budgeted assignments. Thus at most
`A * (1 + max_repairs) * max_assignments` assignments can consume the
retry budget. Expired leases count even when the provider never runs; permanent
failures can end a job before its allowance is used. Candidate attempts are
created only from completed assignment results, not from every claim.
Pre-execution assignment rejections are retained for diagnosis but excluded
from this budget, so malformed or incompatible coordinator responses do not
exhaust work that no provider saw.
Consequently the raw claim/assignment count is not bounded if an incompatible
worker keeps reclaiming the same job. These bounds do not promise a number of
actual model calls, completed candidates, or tokens. The scripted executor emits
a fixed fixture; the Ollama executor passes the requested generation limit as
`num_predict` and reports actual usage when available. A configured Ollama worker advertises
`ollama/<local-model-tag>`, for example `ollama/qwen2.5-coder:7b`.

The `max_repairs` upper bound is coordinator API validation policy, defined by
the named application limit `MAX_REPAIRS`; it is not a deployment option. Schema
integrity requires only that stored repair budgets and depths are nonnegative.

`generation_timeout_seconds` is an integer from 1 through 86400 and defaults to
120. The coordinator persists it on every job and returns it as
`job.timeout_seconds`; workers must use that deadline without substituting a
different valid value. Schema 4 gives existing runs and jobs the previous
120-second behavior.

Both ad hoc runs and experiments accept an optional top-level
`"generation_settings":{"temperature":0,"seed":42}`. Only these two keys are
accepted: temperature is a finite JSON number in [0, 2], seed is an integer in
[0, 9223372036854775807] (booleans are not integers). Omitted keys use provider
defaults; no arbitrary provider options are forwarded. For new ad hoc runs and
experiments, a supplied seed is the base seed: initial jobs in request order
(including across `initial_jobs` groups) receive base + zero-based chain index.
The full range must fit the seed bound or submission fails. Each repair inherits
its parent's effective seed; retries of one job reuse that job's seed. Thus
independent/repair experiment pairs with the same base seed have matching first
initial generations when their model and prompt agree. Temperature applies to
every job. The base settings are persisted on the run and in experiment config
(when supplied); effective settings are persisted per job and shown in
`jobs[]`, `assignments[]`, `attempts[]`, and claim `job.generation_settings`.
Attempt `generation_settings` records the requested settings, separately from
worker-reported `generation` metadata. Previously stored jobs keep their original
settings (including repeated seeds or empty objects); no historical jobs are
reseeded. Older workers may
silently ignore the additive job field, so nonempty settings jobs are leased only
to workers advertising the capability below. Empty/default jobs remain available
to old workers. Submissions with settings for the `scripted` model (including a
group in `initial_jobs`) fail with a configuration error; the scripted executor
also reports a permanent error if another coordinator dispatches such a job.
Ad hoc scripted runs without settings retain their defaults.

`GET /v1/runs/{id}` returns the problem, jobs, assignments, candidate attempts
(`attempts[]`), and verification outcomes. `initial_jobs` reports the effective
ordered initial strategy reconstructed from initial job rows, including defaults.
Adjacent groups with identical model and output budget are coalesced; group labels
or redundant segmentation are not retained. Individual `jobs[]` carry their
persisted model and output budget, including repairs. This works for old databases
without a migration. Lease tokens are never included.
Run states: `running`, `solved`, `exhausted`, `error`. A verifier infrastructure
failure sets `error`; queued jobs
stop. Success sets `solved` and cancels queued jobs. Already dispatched jobs may
finish and their outputs are retained and verified. A Lean-verified proof has
precedence over every other outcome: it changes `running`, `error`, or `exhausted`
to `solved`. Once `solved`, no later verification can downgrade the run. An
infrastructure failure changes only `running` to `error`; other outcomes do not
change an existing terminal state. Thus delivery order cannot change whether a
run containing a verified proof is ultimately `solved`.

The coordinator's verification loop is single-threaded. Across all runs, it
selects unverified candidates in persisted attempt insertion order, then by
attempt ID as an explicit final tie-breaker. Restarting the coordinator does not
change this queue order. This is verification ordering only; it does not define
worker job-claim scheduling.

`GET /health` returns `{"status":"ok"}` with status 200. This is cheap HTTP
liveness and does not inspect Lean, Docker, or the configured image.

`GET /ready` checks whether the configured verifier can accept work. It returns
200 `{"status":"ready"}` when available. It returns 503
`{"status":"unavailable","diagnostics":"..."}` when a prerequisite is missing
or the trusted smoke check fails. Diagnostics are bounded to 8 KiB. Local mode
requires the configured project directory, `lean-toolchain`, `lakefile.toml`, and
a successful trusted `Lean`/`Init` import. Docker mode starts the configured image
with `--pull=never` and asks that image to perform the same trusted smoke check;
this detects a missing Docker executable/daemon, missing image, or unusable Lean
runtime. No theorem statement or candidate proof is accepted by this endpoint.
Unlike `/health`, `/ready` may start Lean or a container and is therefore suitable
for less frequent readiness probing rather than high-frequency liveness checks.
The prototype does not cache readiness results.

## Repair policy

On a `rejected` verification, a running run creates one child job if the parent
job's `repair_depth` is below `max_repairs`. Verification storage and child creation
are one transaction; repeated verification delivery cannot create extra children.
The child inherits the parent job's model, output-token limit, generation timeout
and assignment retry limit; repairs do not switch models or choose another group.
Its `parent_attempt_id` points to the rejected attempt; depth increases by one.

The trusted original problem is carried only by the structured `statement` and
`imports` fields. `messages` is reserved for coordinator strategy or repair
feedback; it does not repeat problem context or specify provider output format.
For a repair, the final user message includes the previous candidate and Lean
diagnostics. Diagnostics are UTF-8 clipped at 8 KiB with an explicit marker; the
complete report is retained in the database. Only the immediately preceding
attempt is included.

Verification timeouts end that chain without a repair. Infrastructure failures
stop the run. Transient execution failures retry the same job under the assignment
limit; permanent execution failures immediately fail that job. Neither advances
repair depth. Completed work arriving after a run is solved or errored is recorded,
but a rejection cannot spawn a new repair.

`GET /v1/runs/{id}` includes `max_repairs` and `max_assignments`, and exposes
`parent_attempt_id` and `repair_depth` on both jobs and attempts (plus `job_id` on
attempts). Schema 3 migrates existing runs with `max_repairs=0`; no old attempts
are rescheduled. Schema 5 adds the run-level assignment policy and gives existing
runs the previous limit of three. Existing jobs retain their stored limits.
Schema 6 replaces the old 0–2 database checks with nonnegative checks while
preserving run values, repair links, foreign keys, and parent uniqueness.

## Claim work

A job is a generation request for its selected model, initially or as a repair. A
claim creates an assignment: a leased dispatch of that job to one worker daemon.
The worker advertises model identifiers it can execute; a provider (such as
Ollama or the scripted fixture) is its model-specific execution adapter, not the
worker or a logical agent. A job can receive multiple assignments after expiry
or transient failure, but a successful result creates one candidate attempt.
Logical agents have no first-class identity in this protocol.

`POST /v1/claim`:

```json
{"worker_id":"homelab-1","models":["scripted"]}
```

Updated Ollama workers opt in with
`"capabilities":["generation_settings"]`. Omission or an empty list means no
support; unknown capabilities, duplicates, and malformed lists are rejected.
Updated Ollama and OpenAI workers also advertise `"model_respond"`, alone or
alongside `"generation_settings"` (either order). Only workers advertising
`model_respond` can claim `model.respond` jobs; older proof-only workers skip
them and still claim eligible proof jobs. The protocol version remains 1 because
the new kind is capability-gated. A worker rejects an unexpected task kind or
malformed task before execution.
The opt-in is a worker claim, not an attestation. It controls leasing only: a
worker lacking it skips nonempty-settings jobs and can still claim later default
jobs in FIFO order among eligible work. The bundled scripted worker does not
advertise it. Old workers remain compatible with the omitted field; use an
updated coordinator to prevent silent settings downgrades.

Returns 204 if no compatible job exists, otherwise 200:

```json
{
  "protocol_version": 1,
  "assignment_id": "opaque-id",
  "lease_token": "opaque-secret",
  "lease_expires_at": 1790000030.0,
  "heartbeat_seconds": 10.0,
  "job": {
    "id": "opaque-job-id",
    "kind": "model.generate",
    "model": "scripted",
    "statement": "(n : Nat) : n + 0 = n",
    "imports": ["Init"],
    "parent_attempt_id": null,
    "repair_depth": 0,
    "messages": [],
    "max_output_tokens": 2048,
    "timeout_seconds": 120,
    "generation_settings": {}
  }
}
```

Times are Unix seconds. The worker uses `heartbeat_seconds` for renewal rather
than relying on synchronized clocks. Worker capabilities are claims, not trusted
attestations. A worker advertises one free slot by making one claim. The worker
applies `job.timeout_seconds` to provider execution; the deadline includes model
loading. Values outside the documented range are rejected as malformed rather
than silently replaced.

Claim scheduling is coordinator-owned global FIFO among compatible work. The
coordinator considers every queued job whose model appears in the worker's
`models` list and whose run is still running, then selects the oldest persisted
job insertion, with job ID as the final deterministic tie-breaker. The order of
the worker's `models` list is not a preference and does not affect selection.
This ordering applies across runs and survives coordinator restarts. Selection,
assignment creation, and the job state change occur in one write transaction,
so concurrent workers cannot claim the same job.

All shown claim-response fields are required (nullable `parent_attempt_id` is
still present as JSON `null` for an initial job). Assignment, lease-token, job,
parent-attempt, and model identifiers are nonempty and at most 256 UTF-8 bytes.
`lease_expires_at` must be a positive finite Unix timestamp; workers decode and
validate it but do not compare it to their local clock. `heartbeat_seconds` is
greater than zero and at most 86400.

`statement` is nonempty and at most 64 KiB. `imports` contains 1–32 nonempty
module strings of at most 256 bytes each. `messages` contains at most 32 entries;
each role is `system`, `user`, or `assistant`, and each content string is
nonempty and at most 256 KiB. `max_output_tokens` is 1–32768 and
`timeout_seconds` is 1–86400. `repair_depth` is nonnegative. Depth zero requires
a null parent; positive depth requires a nonempty parent identifier. A worker
rejects an unsupported `protocol_version` separately from a malformed v1 field,
and neither kind of response reaches its executor. When the response contains a
usable `assignment_id` and `lease_token`, the worker immediately submits the
authenticated rejection described below. It does so before starting heartbeats or
provider execution. If either credential is absent, malformed, or outside its
bound, safe release is impossible; the worker sends nothing and lease expiry is
the fallback.

Providers construct trusted problem context from `job.statement` and
`job.imports`, and exclusively own any provider-specific output-format
instructions. They append `job.messages` in wire order after that context. An
initial job currently has no messages. A repair has one user feedback message,
which therefore remains the final model message. Workers must not remove
messages because their content happens to equal coordinator or theorem text.

### Bounded non-proof model calls (A1)

The coordinator may enqueue one `model.respond` job for a **running** run using
`Store.enqueue_task(run_id, model, task_type, messages, max_output_tokens=512)`.
This is a coordinator-internal operation for later group orchestration, not a
public submission endpoint. Its claim has the same trusted `statement`, `imports`,
lease, timeout and generation fields as `model.generate`, with `kind` set to
`model.respond`, `task_type` one of `plan`, `question`, `finding`, `critique`,
`task_proposal`, and 1–8 bounded strategy messages. Each task message has
`role: "user"` and nonempty content of at most 8 KiB UTF-8; higher-priority
roles are rejected so untrusted task context cannot impersonate instructions.
The coordinator treats these messages and their contents as untrusted context.
The provider constructs the trusted theorem/import context first and owns the
task-specific JSON format instructions; credentials remain worker-local.

For a successful task the result is
`{"status":"completed","output":{"type":"finding","text":"Try induction"},...}`;
`output.type` must match the leased `job.task_type`, and `output.text` must be
nonempty and at most 8 KiB UTF-8. Providers request a JSON object containing
exactly one `text` string; malformed/empty/oversized output is a permanent
`formatting_failure` with bounded `generation.raw_response` and available usage.
The existing optional `usage` and `generation` fields also apply to task
failures. Assignment inspection includes `task_result` for completed task
assignments (otherwise null); `jobs[]` includes `kind`, `task_type`, `messages`.
No task result creates an `attempt`, enters the Lean verifier queue, triggers
proof repair, or marks a run solved. Proof jobs retain their original
`{"text":"..."}` output format and Lean verification.

Transient task failures and expirations use the existing assignment retry
budget; permanent failures end that job. Late results return 409. Identical
resubmissions after an acknowledged result return 200 without duplicating
the result, including after restart; changed results return 409. A malformed
typed result returns 400 while the lease remains active. Run termination is
still the v1 proof-run policy; group lifecycle is a separate later milestone.

## Renew and submit

`POST /v1/assignments/{id}/heartbeat`:

```json
{"lease_token":"opaque-secret"}
```

Returns 200 with `lease_expires_at`. Expired/invalid assignments return 409.

`POST /v1/assignments/{id}/result`:

```json
{"lease_token":"opaque-secret","status":"completed","output":{"text":"rfl"},"usage":{"input_tokens":null,"output_tokens":null}}
```

Output must be a nonempty proof body, at most 128 KiB. Unknown usage is omitted or
null, never assumed to be zero. A provider/executor failure instead submits:

```json
{"lease_token":"opaque-secret","status":"failed","failure_class":"transient","failure_category":"provider_failure","error":"Provider unavailable"}
```

`failure_class` is either `transient` or `permanent`. Transient failures, such as
service/network errors, requeue the job while fewer than `max_assignments`
assignments have been made. Permanent failures, such as invalid worker
configuration or a deterministically malformed provider response, fail the job
immediately. Workers written before this additive field may omit it; the
coordinator treats omission as `transient`, preserving the previous bounded-retry
behavior. Run inspection exposes the effective classification on failed
assignments (and `null` on non-failed assignments).

Failed results may also include `failure_category`: `provider_failure` (provider
transport, status, response, or local provider settings), `formatting_failure`
(invalid, empty, or oversized generated proof), or `other_failure`. This is
independent of retry-oriented `failure_class`. The coordinator persists this
optional category and experiment summaries use it ahead of the error text.
Older workers may omit it; summaries retain the historical Ollama error-prefix
fallback for those results.

A worker that cannot begin execution because the claimed assignment itself is
malformed or uses an unsupported protocol submits to the same result endpoint:

```json
{"lease_token":"opaque-secret","status":"rejected","rejection_kind":"malformed_assignment","error":"job.statement must be a nonempty string"}
```

`rejection_kind` is `malformed_assignment` or `unsupported_protocol`. The
coordinator authenticates it exactly like any result, records the assignment with
status `rejected`, and immediately requeues the job. Rejections do not create an
attempt, advance repair depth, or consume `max_assignments`; they describe a
pre-execution protocol problem, not Ticket 6's transient/permanent executor
failure. Unsupported protocol and malformed assignments have the same state
effect but remain distinct in inspection through `rejection_kind`. Repeated
identical rejection delivery is idempotent; a changed result returns 409.

Both success and failure submissions may include optional `usage` and `generation`
objects. Example generation metadata:

```json
{
  "raw_response": "{\"proof\":\"rfl\"}",
  "raw_response_truncated": false,
  "model": "qwen2.5-coder:7b",
  "finish_reason": "stop",
  "total_duration_ns": 2622969123,
  "load_duration_ns": 2610250,
  "prompt_eval_duration_ns": 420840000,
  "eval_duration_ns": 2182903000,
  "context_length": 4096,
  "max_output_tokens": 256,
  "temperature": 0,
  "seed": 42,
  "model_digest": "sha256:..."
}
```

All fields are optional. Raw response is limited to 128 KiB UTF-8, model and finish
reason to 256 bytes, and numerical fields to nonnegative signed-64-bit integers.
Missing durations stay omitted. Raw response is the unmodified generated content
before extraction, or the HTTP response body if envelope parsing/HTTP execution
failed. Oversized responses retain a prefix with `raw_response_truncated=true`.
Metadata is reported by the worker/provider, not independently attested. For the
Ollama worker, `context_length` is the configured `num_ctx` request option and
`max_output_tokens` is the job's `num_predict` request option. `temperature` and
`seed` appear only when explicitly requested, including on Ollama execution and
format failures with metadata; they describe request options, not an attestation
of what the provider applied. The worker passes them to Ollama's `options` and
reports its response `model` separately from the requested job model. It queries
its configured Ollama `/api/tags` for the exact installed model name and retains
the local SHA-256 digest as `model_digest` when available. Lookup failure or an
unmatched/invalid digest leaves that field absent; the reported model name alone
does **not** identify immutable model contents. No local endpoint or credentials
are recorded in generation metadata. Digest lookup and chat are separate API
calls, so a model replaced between them cannot be detected by this protocol.
Schema 9 adds default-empty settings to old runs and jobs without changing them.

`GET /v1/runs/{id}` exposes generation and usage on assignments (including failed
executions) and completed attempts. `attempts[].model` remains the requested
coordinator identifier; `attempts[].generation.model` is provider-reported.
An additive schema-2 migration supplies empty metadata for existing attempts.
These optional fields preserve compatibility with scripted/v1 workers.

Returns 200 `{"accepted":true}`. This acknowledges storage, not proof validity.
Repeated semantically identical JSON is acknowledged without another attempt.
A changed terminal result, invalid token, or late submission returns 409.
An acknowledged result can be retried after lease expiry and coordinator restart.

Expired/abandoned and transiently failed assignments count toward the run's persisted
`max_assignments` limit. A permanent failure also consumes its assignment but ends
that job without dispatching the unused allowance. Expired work can be reassigned;
late outputs are rejected,
so lost work and unknown usage are visible as expired assignments. Invalid proofs
are completed attempts, not execution failures. They create a new linked repair
job only when the run's repair policy allows it; they never retry the completed
assignment.
