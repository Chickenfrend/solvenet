# Challenge-v1: paired independent vs repair, Goedel-Prover V2 8B

For the rerun with distinct independent-chain seeds, see the [corrected comparison](../challenge-v1-goedel-corrected-2026-09-23/README.md).

**Interpretation correction:** The historical 15/36 independent vs 18/36 repair
comparison below is confounded and is **not a valid comparison of independent
search against repair**. At the time, all three initial jobs in each independent
run received the same seed, prompt and model, so seeded generations were duplicated
instead of sampling three distinct initial chains. In 35 multi-candidate cases,
the outputs were duplicates. The repair arm's first initial generation used the
same base seed, but its later jobs received repair feedback. The linked snapshots
are preserved as records of what ran; the numerical results must not be read as
evidence that repair outperformed three independent generations.

On 2026-09-23, six full-set experiments ran sequentially against the local Ollama model `goedel-prover-v2-8b:q4_k_m` (`sha256:98d095df8e1d58c088000c8a97fe5d4bc28b97fad4ef77d7a794be30544299d1`). All used the exact `problems/challenge-v1.json` bytes at SHA-256 `cd199d3ccd299533a38b14ead2d768b7edf47565f7c6b2d14f63822030d85337`, Lean `leanprover/lean4:v4.19.0`, temperature 0.6, Ollama context 4096 and `max_output_tokens` 256. The independent policy was the default 3 initial jobs / 0 repairs; repair was 1 initial job / up to 2 repairs. Seeds were explicitly set to 11, 22 and 33 in both arms. Both strategies used the same worker binary, SHA-256 `547fdee56149bdb7efdd8748bb22e3a66083044de2a8dac8ba7aea3477019186` (built from commit `1efedef`), and one continuously polling worker. The coordinator used the existing `solvenet.db` and local verifier through the pre-existing `/tmp/opencode/solvenet-lean-bin/lake` wrapper, which executes pinned Lake via `bwrap --unshare-net` with the verification workspace writable. `/ready` returned HTTP 200 before submission. No other experiment was submitted until all 12 runs in the preceding one were terminal, all candidates had a verification status, and there were zero active assignments.

The known/unknown token and provider-time counts include formatting failures, which reported usage and durations despite producing no candidate attempt. All six had **zero provider failures, other failures, expiries, pre-execution rejections, active assignments, and unknown usage values**. Each unsolved run was `exhausted`; no run ended in error. The mean proof time uses the summary's run-creation-to-first-persisted-verification interval for solved runs only, including queue time; provider time is the sum of Ollama-reported durations and Lean time sums verification durations, neither being an experiment wall-clock duration. The observed sequential submission-to-settlement intervals were about 75, 57, 66, 54, 63 and 54 seconds in table order.

Across the three paired seeds, independent solved **15/36 run instances (41.7%)**, repair **18/36 (50.0%)**. Independent used 11,095 input and 5,174 output tokens; repair used 13,735 input and 3,526 output tokens. All token counts were known. At seed 11 the solved problem sets matched exactly. At seed 22 repair additionally solved `nat-add-succ-swap` at depth 1. At seed 33 repair additionally solved `nat-add-cancel` and `list-map-append`, both at depth 1. There were **no depth-2 successes**. Repair did not lose a solved problem relative to independent in any of these three pairs. The 12 fixtures are reused across seeds, so 36 run instances are not 36 independent problems.

As previous **core-v1** context from local DB history, the Goedel-Prover experiment pairs included a 5/12 independent vs 4/12 repair pair (IDs `dd6ab5f93b70414680c4c6c438829b73` / `8f53d1fe95244deeb9e4e391303300fd`) and a 12/12 independent vs 8/12 repair pair (IDs `5dbfbac324e74db4a852f5c955e9ffa5` / `40288a8a9cfb407fa326352510a46e60`). Those earlier results used different fixture/model settings and should not be pooled with this paired challenge comparison; the 12/12 independent core result illustrates possible fixture saturation. This challenge comparison is still exploratory: only three seeds, one model and one fixture set, with different realized token budgets (repair prompts use more input tokens). Equal limits on *possible generations* do not make equal token budgets or equal numbers of actually completed generations; verified attempts can exceed solved-run counts. Format failures and early success also change actual calls. The local database retains full candidate and diagnostic histories; the IDs above and run IDs in the JSON snapshots are local references for `GET /v1/experiments/{id}/summary` and `GET /v1/runs/{run_id}`.

The six linked JSON files are the coordinator's settled, machine-readable summary snapshots. After settlement, completed attempt generation metadata in the database was checked for the exact model name and digest, temperature 0.6, matching seed, context 4096 and output limit 256; the persisted experiment configuration was checked for fixture SHA-256, settings and strategy job/repair defaults. No raw proof or response text is exported here.
